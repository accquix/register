# Architecture v1

**Status: proposal.** The direction is agreed (see [decisions.md](decisions.md)); implementation
has not started.

## Shape

- **One repository, one Go binary (`accquix-register`), one Docker image.**
- **Modes:**
  - `serve`: read-only HTTP API;
  - `sync`: downloads and merges the sources;
  - `migrate`: applies the embedded goose migrations;
  - `openapi`: prints the OpenAPI 3.1 document.
- `serve` and `sync` run independently, so a heavy import never takes CPU from API requests.
- **Not in v1:** UI, multi-tenancy, billing, GraphQL, Kafka, Elasticsearch, Redis, a raw-data
  archive, history.

```text
cmd/accquix-register/        main: serve | sync [--source] | migrate | openapi
internal/config/             env + _FILE secrets
internal/normalize/          name_core, legal-form suffixes, addresses, IČO/DIČ/IČ DPH classification (pure)
internal/sources/{rpo,fs,ruz}/  fetch (ETag, retry) + stream-parse into typed rows; no DB
internal/ingest/             staging COPY, hash merge, absence marking, checkpoints
internal/scheduler/          gocron + PostgreSQL advisory lock
internal/lookup/             composes sections, freshness rules
internal/search/             query planning, keyset cursor
internal/api/                Huma handlers, auth, rate limit, RFC 9457 problems
internal/store/sqlc/         generated (committed)
db/migrations/*.sql          goose, embedded
db/queries/*.sql             sqlc input
api/openapi.yaml             committed; CI fails on drift
testdata/{rpo,fs,ruz}/       SYNTHETIC fixtures only
deploy/compose/              postgres:18 → migrate → serve + sync
```

## Data model

There is **one current-state table per source**, each keyed by its source's own key. The API joins
them by identifier at read time. There is no canonical merged `entities` table: that merge is the
most fragile part, and it fails for FS rows that have no IČO. Provenance is kept per row, because
every API section comes from one table.

| Table | Key | Content |
| --- | --- | --- |
| `rpo_subject` | RPO `id` | IČO (indexed, **not unique**), `kind` (legal_person, sole_trader, public_body, other), `name`, `name_core`, `legal_suffix`, legal form code and text, `established_on`, `terminated_on`, address, current `registrations` (jsonb: kind, office, number, validFrom), `search_suppressed` |
| `fs_tax_subject` | DIČ | `ds_dsrdp`: IČO optional, name, municipality, address |
| `fs_vat_payer` | `IC_DPH` plus IČO or normalised name (VAT groups) | `ds_dphs`: paragraph, `registered_on`, `type_changed_on`, `effective_from`, name, city |
| `fs_list_entry` | (dataset, subject_key) | `ds_dphz`, `ds_dphv`, `ds_dpho`, `ds_iz_ran`; `attrs` typed per dataset in Go |
| `ruz_entity` | RÚZ id | IČO, DIČ, name, legal form, dates; `deleted_at` on `ZMAZANÉ` |

**Columns on every source table:**
- `source_as_of`: the date the agency stamped on the data.
- `row_hash`: SHA-256 over the **exposed** normalised columns, so `changed_at` moves only on a
  change a client can see.
- `first_seen_at`, `changed_at`.
- `absent_since` / `removed_at`: an observation, never a legal date.
- `src_date`, `src_rank` (RPO only): the order guard.

**Normalisation runs in Go** and is shared by ingest and search:
- NFD, strip combining marks, lower case;
- collapse punctuation;
- strip the legal-form suffix (`s.r.o.`, `spol. s r.o.`, `a.s.`, `k.s.`, `v.o.s.`, `š.p.`…) and
  keep it in its own column.

**Indexes:**
- B-tree on IČO, DIČ, IČ DPH;
- GIN `gin_trgm_ops` on `name_core`;
- `text_pattern_ops` on `name_core` for prefixes.

GIN vs GiST is decided by measurement.

**Not stored:** statutory bodies, stakeholders, representatives, residence when it differs from the
place of business, birth data, previous names and addresses, NACE history.

**Natural persons in `ds_dsrdp` without an IČO** (private taxpayers who are not in RPO): DIČ, name
and municipality only, reachable by exact DIČ, left out of name search. Pending confirmation:
OQ-5.

## API v1

The OpenAPI 3.1 document is generated by Huma and committed as `api/openapi.yaml`. Errors are RFC
9457 `application/problem+json` with a stable `code`.

| Endpoint | Purpose |
| --- | --- |
| `GET /v1/lookup/{id}` | The identifier type is detected from its shape: 8 digits = IČO, 10 digits = DIČ, `SK` + 10 = IČ DPH. Anything else is `400 invalid_identifier` |
| `POST /v1/lookup:batch` | Up to 100 ids per call; `fields=versions` returns only the section versions (consumers' change checks) |
| `GET /v1/search?q=&limit=&active=&cursor=` | An identifier gives an exact match. Anything else is a name search: active subjects first, then prefix hits, then `word_similarity`. Keyset paging, 100 results at most. 1–2 characters use the prefix index only |
| `GET /v1/sources` | Freshness, licence and attribution per dataset |
| `/livez`, `/readyz` | Health; no key |

**Lookup response:** a subject has the sections `identity` (RPO), `tax` (FS `ds_dsrdp`, with RÚZ
conflicts), `vat` (FS `ds_dphs`), `risk` (FS lists) and `accounting` (RÚZ). Each section carries:
- `state`:
  - `present`: a row exists;
  - `absent`: the dataset is fresh and has no row;
  - `unknown`: the dataset was never loaded, or it is stale.
- `source {dataset, asOf, changedAt, version, stale}`.

The VAT section returns facts (listed, paragraph, dates, `notListedSince`) and **never**
`vatValid=true`. Every response carries `attribution`.

**Error rules:**
- `404 not_found` only when every consulted dataset is fresh.
- Otherwise `503 unavailable` with a `reason` (`source_stale`, `database`).
- `stale` is a flag on a `200`, not an error.
- `429` carries `Retry-After`.

**Authentication and logging:**
- `REGISTER_API_KEYS="name:sha256hex,…"` holds hashes only, and clients send `Authorization: Bearer`.
- Without keys `serve` refuses to start, unless `REGISTER_ALLOW_ANONYMOUS=true` is set explicitly.
- Rate limiting is an in-process token bucket per key, per instance.
- Logs record the identifier class and the search mode, never `q` or identifier values.

**Freshness thresholds (proposed, OQ-6):** RPO 3 days, FS 2 days, `ds_iz_ran` 14 days.

## Sync pipeline

**Unit of work.** One unit is one RPO daily file, one snapshot part, one FS list version, or one
RÚZ batch. Each unit is **one transaction**: TRUNCATE staging, COPY (`pgx.CopyFromFunc`), validate,
merge, update the checkpoint.
- A kill rolls the unit back.
- A unit already applied with the same ETag or SHA-256 is skipped. If it is re-applied anyway, the
  hash guard writes 0 rows.

**RPO states:** `EMPTY → BOOTSTRAP(part n) → DAILY ⇄ GAP_WAIT → RECONCILE(part n) → DAILY`, plus
`BLOCKED` when validation fails.
- **Bootstrap:** load the newest *complete* snapshot (the manifest plus every listed part) straight
  into the empty table, then build the indexes. Until it is published, `/readyz` reports not ready.
- **Daily:** the next expected date is `applied_through + 1`. If that file is absent, wait. **Never
  apply a later date.** Alert after 24 h.
  - A gap is healed by the next snapshot dated on or after it.
  - If `applied_through` falls behind the oldest retained daily file (more than 45 days), a
    reconcile from a snapshot is forced.
- **Monthly reconcile:** a hash merge of the snapshot, writing only differences. The order guard
  `(src_date, src_rank)` (snapshot = 1, daily = 0) stops a snapshot from overwriting a later daily
  file. Rows missing from the snapshot get an absence mark, but only below a threshold.

**FS, per list:**
1. Conditional GET; `304` means nothing to do.
2. A SHA-256 check against the last applied version.
3. Stream the XML (`encoding/xml`) into staging.
4. Validate: the list date is not older than the last one, the row-count drop is under its
   threshold, there are 0 parse errors.
5. Merge.

A row that disappears gets `absent_since`.

**RÚZ:** a resumable `ruz_pending` queue (LIST ids by watermark, then FETCH details in batches).
The next watermark is the run's start date.

**Checkpoint tables:**
- `sync_source`: state, `base_snapshot`, `applied_through`, `published_as_of`, cursor.
- `sync_unit`: one row per unit, with ETag, SHA-256, counts and status.
- `sync_run`.
- `ruz_pending`.
- `rpo_snapshot_seen`.

**Validation thresholds (proposals; the spike sets them):**
- Each snapshot part has 100 k rows except the last.
- The snapshot total is at least 98 % of the previous one.
- A daily file has at most 50 k records.
- FS row-count drop: at most 3 % (large lists) or 20 % (small lists).
- Absence marking is blocked if more than 0.5 % of rows are absent.

**Concurrency:**
- Only one sync runs at a time: `pg_try_advisory_lock` on a **direct** connection (session locks do
  not work through PgBouncer in transaction mode). Enable TCP keepalives so that a killed process
  releases the lock.
- Row merges take ROW EXCLUSIVE locks and API reads take ACCESS SHARE, so they do not conflict.

**Memory:**
- RPO: gzip → `encoding/json/jsontext` → one record at a time → COPY. About 50–150 MB RSS
  (estimate). Set `GOMEMLIMIT`.
- FS: save the ZIP to a temporary file first, because a ZIP's index is at the end, then stream the
  entry.

## Personal data

- **Minimise at ingest:** a field that is never returned is never stored.
- **Sole traders — returned:** the business name (it contains the person's name; this cannot be
  avoided), the identifiers, the place of business, the register entry, the status and dates.
- **Terminated sole traders:** available by exact lookup, left out of the default search
  (`active=true`).
- **Objections:** an operator command sets `search_suppressed`. The person stays reachable by exact
  identifier and disappears from name search.
- **The deployer is the controller.** `docs/self-hosting.md` will say so (to write).

## Deployment

**Reference: `docker compose`.**
- Services: `postgres:18` (healthcheck), a one-shot `migrate` (exits 0), then `serve` + `sync`.
- Configuration is environment variables only, with `_FILE` variants for secrets. There are no
  default credentials.
- A single VPS with 2–4 GB RAM is expected to be enough. The measurement spike confirms it.

**Any container platform** that runs a long-lived HTTP container plus a scheduled job (1 GB RAM, up
to about 60 minutes) can host it, against any PostgreSQL. Deployment guides to write, informed by
the 2026-11 research:
- **Fly.io:** an always-on machine; the sync as a scheduled or ad-hoc machine; a static egress IP
  if the database allow-lists by IP.
- **Google Cloud Run:** a service plus a Cloud Run Job with Cloud Scheduler.
- **AWS ECS/Fargate:** a service plus an EventBridge-scheduled task.
- **A VM with Kamal or plain systemd timers.**
- **Cloudflare Containers:** possible, but as of 2026-11 the least convenient. The default scheduler
  is deprecated and its replacement is in beta, cron handlers have a 15-minute limit, and there is
  no static egress IP or city pinning.

**Database roles:**
- an API role with SELECT only, which can go through a transaction pooler;
- a sync role with write rights, on a direct connection (advisory lock, COPY);
- a migration role for DDL.

Use TLS `verify-full` to managed databases.

## Integrating a consumer

This is the pattern for an application that uses the register, for example an invoicing tool:

- **Search proposes, only an exact identifier resolves.** The user picks a candidate from
  `/v1/search`, and the application then calls `/v1/lookup/{id}`.
- **Store each section's `version`** with your copy of the counterparty. Check daily through
  `lookup:batch` and show the user what changed.
- **Treat `503 unavailable` and `stale` as "unknown", never as "not found".** An outage must not
  block your workflow.
- **The register entry pre-fills** a supplier's legal line, and the user confirms it. Building the
  genitive court name and the exact wording is the consumer's job.
- **Query VIES yourself** for EU VAT validity. The register does not mirror it.
