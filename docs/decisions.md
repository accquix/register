# Decisions

These are the maintainers' decisions about the project. They bind until a new decision replaces
them; record each change here with its date.

## 2026-11-10: direction

| # | Decision |
| --- | --- |
| D1 | **Our own mirror of the official sources**, no dependency on a paid API. Commercial register APIs charge per request or per year. The free Statistical Office RPO API that many tools used has been gone since RPO moved to the Ministry of the Interior on 2026-06-01, and many open-source integrations broke with it |
| D2 | **Open source, self-hosted.** We publish code only, never data dumps, and we run no public anonymous instance. Every deployment downloads the data itself, and its operator is the GDPR controller of that copy |
| D3 | Licence **Apache-2.0**. Contributions under DCO, no CLA |
| D4 | **PostgreSQL** is the store, from any provider. Cloudflare D1 and similar platform-only stores were rejected because they cannot be self-hosted |
| D5 | The product is a **search and lookup API**. One smart input box takes a name, an IČO, a DIČ or an IČ DPH. Search ignores diacritics, tolerates typos and matches prefixes |
| D6 | **Name search covers everyone**, sole traders included. The operator is responsible for running it lawfully, and the documentation says so |
| D7 | The **register entry** (court, oddiel, vložka, or the trade-licensing office and number) is returned in a structured form, so that consumers can pre-fill a supplier's legal details. The user confirms them there |
| D8 | **No history.** The register keeps the current state, refreshed daily, with `changed_at` per record and a version hash per section. A consumer detects changes by comparing versions |
| D9 | The Financial Administration API key is **optional**. Each operator requests its own key; the daily ZIP exports need none |
| D10 | Own repository, own migrations (goose) |
| D11 | The name is **Accquix Register**; the repository is `accquix/register` |

## 2026-11-10: stack and design (agreed direction; implementation not started)

| # | Decision |
| --- | --- |
| D12 | **Go** for the whole service, one binary `accquix-register` with the modes `serve`, `sync`, `migrate` and `openapi`. Libraries: Huma v2 on chi, pgx v5, sqlc, goose. Rust would be chosen only if measurements show Go missing its memory or CPU budget |
| D13 | Search uses only `pg_trgm` and B-tree indexes. There is no external search engine. Normalisation runs in Go (refined by D17, D18, D29) |
| D14 | `serve` and `sync` are **independent modes** of one image. They can be deployed and scaled separately |
| D15 | **Cloud-independent.** The reference deployment is `docker compose`. Any container platform with scheduled jobs and any PostgreSQL works |

## 2026-11-10: scope

| # | Decision |
| --- | --- |
| D16 | **RÚZ is not part of v1.** For search and lookup it adds almost nothing: identity, legal form and dates come from RPO, and DIČ from the FS list `ds_dsrdp`. Only 3 261 active RPO legal persons (0.65 %) have no DIČ match in `ds_dsrdp` (measured in the spike). Its first load is about 54 h of API calls and needs its own resumable sync. ## 2026-11-10: design after the measurement spike

Based on [spike-results.md](spike-results.md). These close OQ-1, 5–9, 11, 13–15 and 17–20.

| # | Decision |
| --- | --- |
| D17 | **Default search = adaptive v2**, as measured in the spike's third pass. The name-prefix step always runs. The word-prefix step (every query word is the start of a name word, in any order) runs when the name prefix gives fewer than 10 hits or the rarest query word is rare (threshold configurable, initially 1 000 occurrences). It is driven by its rarest word and capped (initially 1 000 candidates). Ranking: exact name, all query words as whole words, name starts with the query, shorter name. **No invented popularity signal** |
| D18 | **Fuzzy search = word-dictionary correction.** Only unknown query words are corrected against the dictionary of distinct name words (trigram, then edit distance with adjacent transpositions), and then run through the default word search. It is **explicit only** (`mode=fuzzy`), never automatic. It is an option, `REGISTER_SEARCH_FUZZY`, default `true`. When it is off, the API answers `fuzzy_disabled`. It has a per-key rate limit, a limit on concurrent fuzzy queries, `statement_timeout`, and `429` without queueing; all are configurable. **The concurrency limit is per instance**: with several `serve` replicas the operator sets a conservative per-replica value, or adds a shared limit, so that the total load on the database stays bounded. The documentation states: *"Fuzzy search is optional, potentially CPU-intensive, and never substitutes exact identifier matching."* |
| D19 | **`GET /v1/capabilities`** reports what this instance offers: fuzzy on or off, limits, API version. `/v1/sources` stays about data freshness only |
| D20 | **Identifiers are matched exactly, never fuzzily.** The IČO check digit (mod 11) is a **warning only**: 778 real RPO IČOs fail it, 16 of them active. An IČO present in RPO is always returned. There is no DIČ checksum until a reliable source confirms one. **An IČ DPH is not a unique subject key**: VAT groups (§4b) share one, so a lookup by IČ DPH may return several subjects |
| D21 | **Subject model.** One subject per valid IČO, with **`registrations[]`** for all its RPO records. The display name comes from the Commercial or Trade Register record, else from the most recently changed record. **Every distinct official name of the subject's active records is searchable.** A record without a valid IČO keeps its own identity by its RPO `id`. An identifier field that is not 8 digits is treated as "no IČO" |
| D22 | **Publication.** The initial bootstrap blocks the API (`/readyz` not ready, `503 reason=bootstrapping`) until all sources are first published and the indexes are built. **The daily sync never blocks a running API**: each unit commits atomically, and the previous consistent data stays served until a unit commits. A repeated full rebuild either loads into separate tables and switches atomically, or runs in an explicitly announced maintenance mode. It never serves a partial state as complete. A stale source does not stop the API: known records are returned with their as-of date, and an unconfirmed absence is `unknown` |
| D23 | **Validation blocks publication.** When an update breaks a threshold, that update is not published, the previous data stays, and the source is marked `blocked` with a diagnostic in `/v1/sources`, plus an alert. **Nothing is truncated or partly applied.** Initial thresholds, all configurable: a daily RPO file has at most 20 000 records; snapshot parts have 100 000 except the last, and the snapshot is at least 98 % of the previous one; an FS list drops by at most 3 % (`ds_dsrdp`, `ds_dphs`, `ds_iz_ran`) or 20 % (small lists); absence marking is blocked above 0.5 % of rows |
| D24 | **Freshness and certainty.** Thresholds: RPO 3 days, FS 2 days, `ds_iz_ran` 14 days. Each section is `present`, `absent` (the source is fresh and has no row) or `unknown` (never loaded or stale), with `asOf`. Booleans derived from a section, such as `vat.payer`, are `true`/`false` only from a fresh `present`/`absent`; otherwise `null` |
| D25 | **VAT section.** It carries `icDph`, `paragraph`, `payer` (from the paragraph: §4, §4b, §5 are payers; §7 and §7a are registered but are not payers), `registeredOn` (nullable), `payerFrom` (nullable; always null for §7/§7a), `typeChangedOn` and `asOf`. Consumers must not print "VAT payer since" for §7/§7a |
| D26 | **Natural persons without an IČO** (`ds_dsrdp` rows outside RPO) are **never in name search**. The exact DIČ lookup returns only the DIČ, name and municipality, only to authenticated API keys, and is unavailable when anonymous access is enabled. The same exact DIČ typed into the search box gives the same, under the same rule (D54). An operator may turn on a full-name search for them (D56) |
| D27 | **Change detection by batch polling** of section versions (`lookup:batch`). There is no `changes?since=` feed. **Versions are deterministic content hashes**, so a rebuild from the sources yields the same versions |
| D28 | **No published client SDK in v1.** Consumers generate types from the committed `openapi.yaml` |
| D29 | **Indexes.** B-tree for identifiers, the name prefix (`text_pattern_ops`) and the word tokens. The only trigram GIN index is on the word dictionary. There is **no GiST and no trigram index on full names** |
| D30 | **Implementation is approved** (2026-11-10), following [architecture.md](architecture.md). It is developed and tested in isolation: no production deployments, no changes to any consumer's databases. These must finish before the first production use, in parallel with development: a test on a real small managed tier (import, fixed-rate load, peak disk; OQ-21), relevance regression tests (OQ-16), and the full RPO chain test after the December snapshot (OQ-2) |
| D31 | **Objections are records of their own** (2026-11-10, after the security review). An objection has a number, the key the operator named, a time and a revocation time; it is anchored to the RPO records that carried its IČO when it was recorded and to records later created with it. What is hidden is computed per record from the current RPO data: an active objection names the record's current IČO, names the record, or is anchored to it. **Nothing is copied onto other identifiers**, so a wrong IČO in a source file never hides another subject for good. An undo revokes one objection by its number and keeps the row |
| D32 | **Fail closed after a rebuild** (2026-11-10). The API does not serve (`503 reason=setup`, `/readyz` not ready) until the operator confirmed the objections of the installation: `suppress --restore` (a backup put back) or `suppress --init-empty` (a new installation with none). An empty database cannot tell the two apart, so the register does not guess. A database that had already published when this was introduced counts as confirmed |
| D33 | **Four database roles** (2026-11-10): migrate (owner), sync (writes the mirror, reads the objections), operator (changes the objections), API (reads the published data and which keys are suppressed, never the reasons). `migrate` applies the per-table privilege matrix for the roles named in `REGISTER_DB_ROLE_*`. PostgreSQL 16–18 stay supported and are tested |
| D34 | **A first publication needs a whole, settled snapshot** (2026-11-10): manifest and bucket agree on parts 001..N, every file has been in the bucket for a settle period, the snapshot is not clearly smaller than the previous one in the bucket, and the total reaches a floor. Every FS list has a row floor. Each of these can be overridden only by explicit configuration, which the sync logs on every pass |
| D35 | **Source dates** (2026-11-10): the date in a file name must be a real date; `exportDate` must be within a tolerance of it and not in the future; updates are ordered by the file-name date; an FS list date may be at most one day ahead |
| D36 | **MCP adapter** (2026-11-11), following [mcp.md](mcp.md): a read-only MCP endpoint `/mcp` in `serve`, **off by default** (`REGISTER_MCP`), stateless Streamable HTTP with JSON responses, the same API keys, limits and logging rules as REST. Three tools (`search_subjects`, `lookup_subject`, `get_data_freshness`); each tool calls the REST handler in process, so its result is the REST body. No batch tool for now. A local stdio adapter (`accquix-register mcp --url`) serves the same tools over the REST API and never touches the database. Library: the official Go SDK (`github.com/modelcontextprotocol/go-sdk`). The tool list is committed (`api/mcp-tools.json`) and checked like the OpenAPI document |
| D37 | **Search cards carry the full address** (2026-11-11, maintainer decision). Every search result, by name or by identifier, includes `address` (street, building number, PSČ, municipality, country): the registered seat or place of business as RPO publishes it, from the same record and in the same order as the lookup's identity section. It is part of the business's public register entry, which this project stores and returns; residence when it differs from the place of business is still never stored. `municipality` stays for compatibility |
| D38 | **Items without a usable identifier are left out, not fatal** (2026-11-11, answers OQ-37). An FS list item with no DIČ, IČO and IČ DPH at all cannot belong to any subject the register can name, so it is skipped; so is an item of the DIČ list (`ds_dsrdp`) with a valid IČO but no DIČ yet, as for a business registered a few days ago. Each is counted in the unit log and in `/v1/sources` (`skippedItems`); more than 100 in one file blocks the list. Every other problem still rejects the file (D23): a malformed identifier, a missing key next to another identifier, a bad date. Such items are never matched to RPO by name or address. A subject's tax section stays `absent` when the list has no row for it: "not in the list as of this date", never "has no DIČ". Register confirms what is known; it is never a precondition for working with a business it does not hold |
| D39 | **Overload protection** (2026-11-11, maintainer decision, answers OQ-38). `serve` admits at most a fixed number of data requests at once (`REGISTER_MAX_IN_FLIGHT`, default: the size of its connection pool), so a request never waits for a database connection after it was admitted. A request that finds no free slot waits a short time (`REGISTER_ADMIT_WAIT`, default 250 ms), then gets `503` with `reason: overloaded` and `Retry-After`. `429` stays the answer for a caller over its own quota. Health checks, `/v1/capabilities` and `/mcp` itself are not limited (an MCP tool call is limited as the REST call it makes). Measured cause: [managed-postgres-results.md](managed-postgres-results.md), finding 2 |
| D40 | **API connection pool default** (2026-11-11, maintainer decision, answers OQ-39). When `REGISTER_DATABASE_URL` sets no `pool_max_conns`, `serve` opens at most 10 connections, whatever the host's CPU count; `pool_max_conns` still overrides it. The startup log states the pool size and the in-flight limit |
| D41 | **Demo mode** (2026-11-11, maintainer decision, answers OQ-31). `accquix-register demo` loads a few hundred fictional subjects into an empty database through the normal sync code, from an in-process copy of the source layouts, and marks the database as a demo for good. A demo database answers like a real one, but every attribution says the data are fictional, `/v1/capabilities` reports `demo: true`, `/readyz` says so, and `sync` refuses to write into it. `demo` refuses a database that holds real data. `deploy/demo/compose.yaml` runs PostgreSQL, the demo loader and `serve` with no secrets and anonymous access on localhost only, as a separate compose project, so it cannot share a volume with a real installation |
| D42 | **Objection links have a provenance and can be released** (2026-11-11, maintainer decision after the second independent review; refines D31). An objection and its links to RPO records are separate things. A link records the objection, the stable RPO record id, its basis (`at_objection`, `carried_ico`, `restored`, `migrated`), the sync unit and the time. Every unit links the records it sees carrying an objected IČO, so no record leaves an objection without the operator; a link never extends to other records with the record's new IČO. The register **errs towards hiding and says so**: a wrong IČO in a source file can hide one record of another subject, which is a documented limitation, never a silent or transitive one. The operator releases one link (`suppress --release`); the release is kept, so the sync does not re-create the link. Import and objections are serialised, so a record is never searchable between the two |
| D43 | **Stability policy** (2026-11-11, maintainer decision, answers OQ-35), following [stability.md](stability.md). Releases follow Semantic Versioning, starting with `1.0.0-rc.1`; a release candidate freezes the contracts of the coming release. The contracts are the HTTP API under `/v1`, the MCP tools, the command line, the configuration, the objection backup format and the meaning of the answers; the database schema, `internal/`, logs, search ranking, error texts and default limits are not. New fields and new values of open enumerations (`code`, `reason`) are compatible; consumers must ignore unknown fields. A removal is marked deprecated (OpenAPI, `Deprecation` and `Sunset` headers, changelog), works for at least 6 months and goes only in a major version; a new HTTP API major version is served next to the old one. Every release has an entry in `CHANGELOG.md` |
| D44 | **A snapshot is one consistent set of content** (2026-11-11, maintainer decision after the second independent review, finding D5). A snapshot is identified by a fingerprint of its manifest and of every part's name, size and ETag, not by its file names. If the fingerprint changes while the snapshot is being applied, the bootstrap or reconcile starts over; nothing applied from the old set is published with the new one. Downloads are verified against the listed ETag (the bucket gives MD5 ETags), a local copy is reused only for the same ETag, and the fingerprint is checked again before a publication and before absence marking |
| D45 | **Upgrades rebuild the search layer; grants are verified** (2026-11-11, maintainer decision after the second independent review, findings D4, D6, D7, D11, D12). A migration that changes what is hidden marks a search rebuild as owed; the API answers `503 reason=setup` until the next sync pass has rebuilt the layer. `migrate` refuses role names that would make the privilege matrix meaningless (the owner, a superuser, a role with memberships), revokes rights given to `PUBLIC`, and asks PostgreSQL for the effective rights before it commits. A file named for a day after tomorrow is ignored. Advisory locks cannot be withheld from a role that can connect: the API's database credentials are part of the trust boundary |
| D46 | **Source files are parsed within fixed limits** (2026-11-11, maintainer decision, release hygiene): download size, decompressed size, record and element size, record and item count, entries in a ZIP. Over a limit the unit is rejected (D23). The limits are constants with headroom over the measured volumes, not configuration. Every parser of untrusted input (the RPO decoder, the FS decoder, the normaliser, the objection backup reader) has a native fuzz test, run briefly in CI |
| D47 | **Supply chain of the build** (2026-11-11, maintainer decision, release hygiene): every GitHub Action is pinned to a full commit SHA with its version in a comment; goreleaser and govulncheck are pinned to a version; dependabot updates Go modules, Actions, the Docker base images and the site's npm packages; CI scans the built image and fails on a HIGH or CRITICAL vulnerability that has a fix |
| D48 | **The legal assessment of objections is the operator's** (2026-11-11, maintainer decision, answers OQ-41). The project does not commission a legal review of the objection model. The model (D31, D42) is a protective default: it hides an objected subject from name search and keeps exact lookup, and it is documented with its limits. Each operator, as the controller of their copy, decides with their own counsel which objections they must honour, on which legal basis they process the data, and whether the default fits their use. The documentation says so plainly; it gives no legal advice |
| D49 | **Install from a release** (2026-11-11, maintainer decision, answers OQ-33). A tag `v*` publishes the binaries (Linux and macOS, amd64 and arm64) with checksums and build provenance, the multi-arch image `ghcr.io/accquix/register:<version>` with an SBOM and provenance, and `accquix-register-deploy_<version>.tar.gz`: `deploy/compose`, `deploy/paas` and `deploy/demo` with the image pinned to that version and the `build:` sections removed (`deploy/package.sh`), so an instance starts without cloning the repository |
| D50 | **Search relevance test set** (2026-11-11, maintainer decision, answers OQ-16). `internal/search/relevance_test.go` runs every ranking rule and every promise of the search documentation as a case on a synthetic register loaded through the real sync code: the exact name first, the legal form and diacritics ignored, a whole word before a word prefix, a shorter name first, word order ignored, the start of any word, two subjects with one name both proposed, closed and objected subjects never proposed, a two-letter query, and fuzzy corrections of a dropped letter, a swap and a wrong letter. Checks on the real data stay local and are never committed. The set found that fuzzy search could not correct a word of up to four letters, which D18 promises: such a word has too few trigrams, so it is now checked against every word one edit away (about 300 exact dictionary reads, about 20 ms on the real data). Known limit, documented: inflected forms are different words (`lipa` does not find "U Lipy") |
| D51 | **A restore never changes what the database has** (2026-11-11, maintainer decision after the independent review of the objection commits). An objection or a link that exists is kept exactly as it is; a backup's release applies only to a link the database lacks. A release needs an existing link. `migrate` judges a role by its effective rights, inherited ones included, instead of refusing every membership, and changes rights only on the register's own tables. The rebuild owed after an upgrade is done by any sync pass and by the demo loader |
| D52 | **An IČO without a DIČ yet is normal, with no limit** (2026-11-12, maintainer decision; refines D38). A new business is registered in RPO days before the Financial Administration assigns its DIČ, so items of the DIČ list (`ds_dsrdp`) with a valid IČO and no DIČ are expected (none in the file of 2026-11-12, where all 41 left-out items had no identifier at all). They are left out (there is no DIČ to hold) and counted apart (`itemsWithoutDic` in `/v1/sources`), and never count against the cap of D38, which now applies only to items with no identifier at all (no DIČ, IČO or IČ DPH): those still cannot be named, and more than 100 in one file still blocks the list (the cap is per list since D53). Items with a DIČ and no IČO are unchanged |
| D53 | **The cap on items without any identifier follows each list's size** (2026-11-12, maintainer decision; refines D38 and D52). A fixed 100 per file was too tight for the DIČ list, the only list that has such items (6 on 2026-11-10, 41 on 2026-11-12, of 1.42 million), and too loose for a small list. Each list now has a cap: a share of the file's items, with a floor and a maximum. `ds_dsrdp`: 0.05 %, at least 10, at most 1000 (about 700 today); every other list: 0.01 %, at least 10, at most 100. Above the cap the version is rejected and the list blocked with the previous data kept (D23); the maximum stops a broken file before its end. A version whose count grew more than threefold and by more than 20 since the version before is applied, with a warning in the log and in the list's `diagnostic` in `/v1/sources`, which the next quiet version clears. `/v1/sources` also gives `items`, the items kept, so the share can be read. `REGISTER_FS_MAX_UNIDENTIFIED` replaces every cap with a count for a run, to accept a version whose count grew for a known reason; like every loosened check it is logged on each pass |
| D54 | **An exact DIČ of a taxpayer without an IČO is answered in the search box** (2026-11-12, maintainer decision; refines D26). The box already resolves an exact identifier the way the lookup does, so a DIČ of a natural person without an IČO (mostly landlords and other private taxpayers) gives one card of `kind: taxpayer` with the DIČ, the name and the municipality: exactly what the lookup returns, never an address, and under the same rule: only on an instance without anonymous access. Name search is unchanged: such a person is never found by name. The card kind is a contract addition made before the 1.0.0-rc.1 tag |
| D55 | **Per-key rate limits are off by default** (2026-11-12, maintainer decision). An instance is self-hosted and usually serves one application with one key, so a default per-key limit only caps the operator's own traffic (the managed PostgreSQL test of 2026-11-11 ran with the limits raised for this reason). `REGISTER_RATE_PER_SECOND` (burst `REGISTER_RATE_BURST`, by default twice the rate) and `REGISTER_FUZZY_EVERY` set them when several applications or clients share an instance; `/v1/capabilities` shows them. What protects the database stays on: admission control (D39), fuzzy concurrency per instance (D18), query timeouts. Anonymous callers are always limited per client IP: 20/s, burst 40, and one fuzzy search per 5 s (`REGISTER_ANONYMOUS_RATE_PER_SECOND`, `REGISTER_ANONYMOUS_RATE_BURST`, `REGISTER_ANONYMOUS_FUZZY_EVERY`) |
| D56 | **Taxpayer name search behind a switch, by the full name only** (2026-11-12, maintainer decision; refines D26). The DIČ list holds about 159 000 taxpayers without an IČO (2026-11-12), mostly private persons such as landlords, and anyone can already look a name up in the Financial Administration's public list; an operator may need the same in their own application. `REGISTER_SEARCH_TAXPAYERS` (off by default) lets name search find them, narrower than the search for businesses: the full name only (every word of the folded name and no other, in any order; no prefixes, no fuzzy, at least two words); the default mode only; only with an API key, and refused together with anonymous access; the same three fields as the lookup (DIČ, name, municipality), never an address; at most five, after the businesses and only in the room they leave; only from a fresh DIČ list (`taxpayers: stale` otherwise, never an empty answer that looks like an absence); a separate limit per key (1/s, burst 10: a person typing a name, not a harvest of the list; about 86 000 probes a day per key, on a list anyone can download whole) above which the search answers without taxpayers and says so (`taxpayers: rate_limited`). A person objects by DIČ (`suppress --subject <DIČ>`): an objection with no links, checked on every query through `objection_active`, so no rebuild, restore or upgrade can lose it before it applies; a DIČ of a subject with an IČO is refused (object by the IČO). When the DIČ list later gives an objected DIČ an IČO, the sync links that IČO's RPO records to the objection (basis `dic_list`, logged like every link): a person who objected never comes back into name search by registering a business, the link stays when the list changes again, and the operator can release it. An objection by IČO or by record also covers DIČ rows that may be the same person (on 2026-11-12, 35 343 DIČ-only rows had exactly the name of an RPO sole trader; an IČO may also be missing or malformed in the DIČ list): when an objected subject's name holds the query's full name as adjacent words, no taxpayer is returned for that query, namesakes included; words scattered across a name do not count. The taxpayer limit is per key: an instance that serves one application with one key shares it among all that application's users, which the operator sets accordingly. The register errs towards hiding, as in D42. Whether an operator's use has a legal basis is the operator's decision (D48). The key is built in Go from the query and in SQL (`register_name_key`, migration 00007) from the stored folded name; a test keeps them equal. Measured on the real list: the index builds in under a second and takes 5 MB, a query takes under 1 ms |
