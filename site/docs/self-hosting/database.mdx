## Roles

Separate roles keep the API read-only:

```sql
CREATE ROLE register_migrate LOGIN PASSWORD '…';   -- owns the schema, runs migrate
CREATE ROLE register_sync    LOGIN PASSWORD '…';   -- sync and suppress
CREATE ROLE register_api     LOGIN PASSWORD '…';   -- serve

ALTER DATABASE register OWNER TO register_migrate;
GRANT TEMPORARY ON DATABASE register TO register_sync;

-- rights on everything migrate creates, now and in later versions:
ALTER DEFAULT PRIVILEGES FOR ROLE register_migrate IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE, TRUNCATE ON TABLES TO register_sync;
ALTER DEFAULT PRIVILEGES FOR ROLE register_migrate IN SCHEMA public
  GRANT USAGE ON SEQUENCES TO register_sync;
ALTER DEFAULT PRIVILEGES FOR ROLE register_migrate IN SCHEMA public
  GRANT SELECT ON TABLES TO register_api;

-- the API never writes, and the server cuts a runaway query too:
ALTER ROLE register_api SET default_transaction_read_only = on;
ALTER ROLE register_api SET statement_timeout = '10s';
```

Run it as an administrator before `migrate`. The docker compose deployment does this for you when PostgreSQL first
starts, so no register process connects as the superuser. On PostgreSQL 17 and 18, also grant `MAINTAIN` on the
tables to the sync role.

Then point each mode at its role:

| Variable | Role | Connection |
| --- | --- | --- |
| `REGISTER_MIGRATE_DATABASE_URL` | `register_migrate` | Direct |
| `REGISTER_SYNC_DATABASE_URL` | `register_sync` | **Direct** (advisory lock, COPY, temporary tables) |
| `REGISTER_DATABASE_URL` | `register_api` | Direct or a transaction pooler |

The sync creates temporary tables, so its role needs `TEMPORARY` on the database. Never give `serve` a role that can
write. Use `sslmode=verify-full` for managed databases.

## Managed providers

| Provider | Notes |
| --- | --- |
| PlanetScale Postgres | Compatible with `pg_strict`: the register never runs `UPDATE` or `DELETE` without `WHERE`. Port 5432 for the sync, 6432 (PgBouncer) for the API. |
| Neon | Works. On Launch plans the database has no IP allow-list, so rely on TLS and the role passwords. |
| Supabase, RDS, plain PostgreSQL | Work as they are. |

## Size and growth

About 2.3 GB of data with indexes, growing with the registers (a few percent a year). The word dictionary used by
fuzzy search adds about 10 MB.

## Back up the objections

The register data needs no backup: it can always be rebuilt from the official sources. Section versions are content
hashes, so after a rebuild your consumers see the same versions and no false changes.

The list of objections (`search_suppression`) is different: it is your own data, and no source can restore it. If it
is lost, every person who objected silently returns to name search. Dropping the database, `docker compose down -v`
and `migrate down-to 0` all delete it.

```sh
accquix-register suppress --list > objections.tsv        # after every change, and on a schedule
accquix-register suppress --restore objections.tsv       # on a rebuilt database, before the first sync
```

Keep the file encrypted and away from the database: it lists the people who objected. Its last line holds a row
count and a checksum, and a restore refuses a damaged file. When you rebuild, run `migrate`, then the restore, and
only then `sync` and `serve`.
